# youtube Coding Style

Coding rules for the YouTube Web E2E automation framework (Playwright + playwright-bdd 8.x).
This file is the **single source of truth for agents implementing steps / Page Objects / components / fixtures**; design rationale and full examples live in
`youtube/docs/` and are not duplicated here.

## 0. Scope and Red Lines

- **Editable**: under `youtube/`: `src/`, `tests/ui/*.steps.ts` (hand-written step definitions), `config/`, `docs/`, `*.config.*`
- **Not editable (generated artifacts)**: `tests/.features-gen/` — regenerated by bddgen from `.feature` + steps; do not hand-edit
- **Editable (confirm first every time)**: `.feature` files — `testcases/` is the single source of truth; **before any change (add/remove scenario, edit step, edit tag) you must ask the user first and get confirmation before editing**
- **Ask the user before every commit / push**
- **All code comments in English**; write the "why", not the "what"
- **Hard comment cap**: at most **1 line** per added/modified block, describing only "non-obvious why or gotcha". Explanatory comments are forbidden ("what it does" / "what changed" belong in the diff and commit message). **Prefer 0 lines over padding.**
- Follow the existing style of each file (indentation, naming, idioms); do not slip in unrelated refactors
- **Names must be self-explanatory**:
  - Name variables / parameters by "what they are" (`videoId`, `searchResultsPage`, `query`); no meaningless abbreviations (`a`, `p`, `tmp`, `data2`)
  - Single-letter parameters are allowed **only** in a one-line short `.map()`/`.filter()` where the meaning is obvious (`.map((s) => s.id)`); once the callback spans multiple lines or branches, switch to a full noun
  - Booleans use `is`/`has`/`can` prefixes (`isVisible`, `hasResults`); collections use plurals (`videoLinks`, `tabs`)
  - Abbreviations limited to team-accepted words (`ctx`, `id`, `url`, `ui`); `ctx` must carry a semantic prefix (`searchCtx`)

## 1. Layering and Dependency Direction

```
.feature (from the main testcases/ library — business scenarios; editable but confirm first each time)
   │ bddgen generates → tests/.features-gen/*.spec.js (do not hand-edit)
   │ maps to (hand-written)
tests/ui/*.steps.ts       ui test layer: thin bridge Gherkin → POM calls (includes assertions)
   │ calls
src/pages/*.page.ts       Page Object: encapsulates UI operations (WatchPage / SearchResultsPage / ChannelPage / HomePage)
   │ uses
src/components/*.ts       reusable UI components (extend BaseComponent, depend only on Page)
src/utils/*.ts            pure utilities (string / element-wait / logger)
```

> Layering principle: `tests/` = test layer (hand-written step definitions + generated spec), `src/` = reusable infrastructure (POM / component / fixture / util). Dependency direction is `tests/ → src/`.

**Dependencies may only point downward — never upward, never bypass a layer:**

| Layer | Forbidden |
|---|---|
| steps | operating `page` directly, writing selectors, writing business logic (except assertions) |
| pages | touching `testInfo`, depending on steps / fixtures, using `waitForTimeout` |
| components | depending on other Page Objects, coupling to test infra |

## 2. BDD Declarative (implementation must support declarative style)

A step describes **user intent (WHAT)**, not UI operations (HOW). If a business action needs multiple UI steps to express →
**add a composite method in the Page Object**, do not stuff imperative steps into the step definition.

```typescript
// ✅ step maps to one business action
When("I open the search filters", async ({ searchResultsPage }) => {
  await searchResultsPage.openFilters();   // composite method encapsulates clicking the button + waiting for the dialog to be visible
});

// ❌ step operates page directly / broken into multiple UI steps
When("I click the filter button", async ({ page }) => {
  await page.getByRole("button", { name: "Search filters" }).click();
});
```

## 3. Step Definition Rules

- Each step takes `Given/When/Then` from `createBdd(test)`, with `test` from `../../src/fixtures/test.fixtures`
- **Thin**: do only three things — "parse parameters → call POM method → assert"
- Inject Page Objects via fixture (destructure `{ searchResultsPage }`); **do not `new` them yourself**
- Use the `ctx` fixture for cross-step state (so POMs stay stateless); do not use module-level variables
- Reuse first: for a new scenario, look for an existing step (`npx bddgen export` lists registered steps), rewrite synonymous phrasing into the existing wording, do not invent new ones
- Name step files by domain `{domain}.steps.ts` (existing: `home` / `search-results` / `watch` / `channel`); put cross-domain generic steps in `common.steps.ts`

## 4. Page Object Rules

- Extend `BasePage`; **declare selectors together at the top of the class** (DOM changes touch one place only)
- Name methods with **business semantics** (`openFilters()` / `applyFilter()`), not UI semantics (`clickFilterButton()`)
- **composite method**: combine multiple UI operations into one business action for declarative steps to call
- **selector priority** (the YouTube site has no `data-testid` under our control, so testid is not first):
  1. `getByRole` / `getByLabel` (buttons, links, headings, tabs, etc. with a clear role + visible name; **first choice**)
  2. `getByText` (only where copy is stable; be careful with i18n-sensitive text)
  3. semantic attribute selectors (e.g. `a[href*="/watch?v="]`, for list items where the site has no stable role)
  - **Forbidden**: structural CSS (`nth-child`, long class chains), XPath — sources of flakiness
- **Wait strategy**:

  | Situation | Usage |
  |---|---|
  | Asserting UI state | `await expect(locator).toBeVisible()` (auto-wait, most common) |
  | After navigation | `await page.waitForURL(pattern)` |
  | **Forbidden** | `page.waitForTimeout(ms)` — arbitrary sleep is a source of flakiness |

- Naming: class `{PascalCase}Page`, file `{kebab-case}.page.ts` (existing: `watch.page.ts` / `search-results.page.ts`, etc.); split into per-domain subdirectories when pages exceed 5

## 5. Component Rules

- Extend `BaseComponent`; the constructor takes only `Page`
- Encapsulate cross-page shared UI blocks (e.g. top bar / side navigation / dialog); do not include page-specific business flows

## 6. Fixtures Rules

- **Modular**: one `{domain}.fixtures.ts` per domain defines fixtures; `test.fixtures.ts` only does `mergeTests()`, **contains no fixtures itself** (prevents a God File)
- Existing fixtures: `home.fixtures.ts` / `search-results.fixtures.ts` / `watch.fixtures.ts` / `channel.fixtures.ts`
- New Page Object → edit the corresponding `{domain}.fixtures.ts`; do not touch `test.fixtures.ts`
- New domain → create `{domain}.fixtures.ts`, import it in `test.fixtures.ts` and add it to `mergeTests()`
- **Guest/logged-out**: YouTube tests need no login, config does not attach `storageState`; **do not write "I am logged in" in Background** and do not create a setup project

## 7. Test Data Rules

- YouTube uses **fixed test data**: video IDs (e.g. `jydYq7oAtD8`), channel handles (e.g. `@freecodecamp`), search keywords (e.g. `playwright`), passed into steps from `.feature` via double quotes
- **No** API data creation, **no** factory layer; test data is public content that stably exists on the external site
- When choosing fixed data, pick "long-lived, unlikely to be taken down" targets to reduce flakiness

## 8. Tags Rules

- Always reference tags in code via the `Tags` constants in `src/data/tags.ts`; do not write bare strings
- `.feature` tag rules are in `.claude/rules/gherkin.md`; ask the user to confirm before editing `.feature`
- **`@quarantine`**: temporarily isolate a known flaky test → still runs locally (for debugging), auto-excluded in CI (`grepInvert`); must attach a Jira ticket to track the root cause, remove immediately once fixed, review every Sprint (>5 is a quality signal)

## 9. Screenshot / Trace Strategy

- "**Keep nothing on pass, keep only on failure**": use the official config `screenshot: "only-on-failure"` + `trace: "retain-on-failure"` (see `playwright.config.ts`); do not write custom step-by-step screenshot hooks
- Failure screens and traces are presented inline by `playwright-smart-reporter` (history / trends / failure clustering); the reporter is an off-the-shelf package, no customization needed

## 10. Logging

- Use `createLogger(this.constructor.name)`, not `console.*`
- Human-readable + colored locally; `CI=true` or `LOG_FORMAT=json` outputs NDJSON (fixed fields `timestamp/level/context/message`, `data/error` optional)

## 11. Toolchain and Verification

- Generate spec: `npx bddgen` (reads `.feature` files from the main `testcases/` library, produces `tests/.features-gen/`, and lists unimplemented steps)
- `missingSteps: "skip-scenario"`: scenarios with unimplemented steps are marked fixme and skipped, **without blocking other tests** — so main-library `.feature` files may exist ahead of automation
- Run tests: `BROWSER_CHANNEL=chrome npx playwright test` (a workaround when bundled chromium cannot be downloaded locally; not needed when using the official docker image); **run only the relevant subset** (pass a `.features-gen/...spec.js` path or `--grep @tag`, or use scripts like `npm run test:search`)
- Before committing, pass: `npm run check` (`type-check` + `format:check` + `lint`)

## 12. Forbidden List (anti-patterns)

- ❌ writing selectors / operating `page` / writing business logic in a step
- ❌ `page.waitForTimeout(ms)` arbitrary sleep
- ❌ Page Object exposing UI-semantic methods (`clickXxxButton`)
- ❌ using structural CSS (`nth-child`, long class chains) or XPath
- ❌ writing fixtures in `test.fixtures.ts` (merge only)
- ❌ bare tag strings, `console.log`
- ❌ meaningless abbreviations / single-letter variables in multi-line logic (`a`, `p`, `tmp`) — naming rules in §0
- ❌ editing `.feature` files, or committing/pushing without being asked
- ❌ decorator steps / Cucumber World (conflicts with the declarative + matrix workflow, deliberately not adopted)
